## `input/first-review.md`

### What The File Is About

This is a product brief for improving TalkToBudda's `Character Selection` experience. It defines the problem, V1 goal, funnel metrics, first-time recommendation rule, UI constraints, returning-user state, non-goals, and later validation questions.

### What Is Good

- The V1 scope is clear and appropriately narrow: descriptions plus one recommended starter badge.
- Analytics event semantics are concrete enough to avoid common implementation drift, especially the distinction between opening chat and sending the first message.
- The recommendation logic is simple, explainable, and avoids premature personalization.
- The brief includes a useful decision rule for what to do if conversion improves but character exploration drops.
- Returning-user behavior is defined well enough to protect existing exploration and last-selected-character behavior.
- Non-goals are explicit, which should reduce scope creep during design and engineering handoff.

### What Is Weak, Risky, Or Unclear

- "First-time user" is mostly defined by first sent message, but the storage owner and persistence boundary are still open.
- The success criteria intentionally avoid numeric targets, which is acceptable for a brief but weak for release governance.
- "Overly concentrated" and "exploration remains acceptable" need thresholds before post-release analysis.
- The brief says to finalize copy for the complete roster, but only includes examples for four characters.
- Dynamic type and localization constraints are mentioned, but there is no acceptance test or design fallback for text overflow.
- The edge case where a user opens selection, leaves without messaging, then returns remains unresolved.

### Specific Improvements

- Add an implementation note naming the owner of first-time state, such as local persistence, user profile state, or analytics-derived state.
- Define a minimum conversion lift or confidence rule before the release review.
- Define a maximum acceptable concentration share for the recommended character.
- Add the full role-description copy set before implementation starts.
- Add acceptance criteria for two-line truncation, dynamic type, and localization expansion.
- Resolve whether the recommended badge remains visible when a user returns after viewing selection but before sending a message.

### Final Score

9.0/10

The brief is strong and implementation-ready at the product level. The remaining gaps are mostly measurement thresholds and delivery acceptance criteria.

## `input/second-review.md`

### What The File Is About

This is a review brief for evaluating conversation quality across TalkToBudda characters using the app's actual prompt setup, model route, API configuration, and a shared set of test questions.

### What Is Good

- The scope lists the characters to review explicitly.
- The evaluation dimensions are practical: voice consistency, differentiation, helpfulness, safety, language handling, and prompt fidelity.
- The shared question set should make cross-character comparisons easier.
- The constraints correctly call out secret handling and prohibit source edits during the review run.
- The output format is clear enough to produce comparable character-by-character findings.
- The brief separates prompt issues from model issues, which is important for actionable follow-up.

### What Is Weak, Risky, Or Unclear

- The brief requires using the same API route and model as the app, but does not state where reviewers should find or verify those values.
- The test set only covers emotionally reflective prompts; it does not include religious sensitivity, factual claims, refusal behavior, or Vietnamese/localized inputs.
- Safety criteria mention crisis mishandling but the suggested questions do not include a crisis-adjacent test case.
- There is no scoring rubric, so final scores may vary significantly between reviewers.
- "Same language as the question" is evaluated, but all suggested questions are English.
- The character list may drift from the live roster unless it is tied to a source of truth.
- There is no guidance on sample count per character beyond "same small set," so the review may under-sample model variability.

### Specific Improvements

- Add a source-of-truth section naming the exact files or app objects to inspect, such as `PromptBuilder` and the chat service configuration.
- Include at least one Vietnamese test question to validate language matching for the expected user base.
- Add one safety boundary prompt that tests crisis-aware escalation without forcing unsafe content into the report.
- Define a score rubric, for example separate 0-10 sub-scores for distinctness, helpfulness, safety, and prompt fidelity.
- Require at least two runs for one or two representative prompts if model variability is a known risk.
- Tie the character list to the live roster source, or require reviewers to note any mismatch.
- Add a "do not quote full model outputs" rule to keep reports concise and avoid leaking unnecessary generated content.

### Final Score

8.2/10

This is a useful and actionable review brief, but it needs stronger source-of-truth guidance, multilingual coverage, and a scoring rubric before it can produce consistently comparable results.
